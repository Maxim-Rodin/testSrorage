# Пояснительная записка к архитектуре складского приложения

## 1. Назначение проекта

Проект `testSrorage` является WPF-приложением складского учета на C# .NET Framework с использованием MySQL. Программа позволяет вести учет товаров, приходов и расходов, редактировать записи, удалять данные и формировать отчеты по выбранному периоду.

После рефакторинга проект построен по слоям:

- `Domain` - доменные модели и атрибуты;
- `Application` - интерфейсы и бизнес-логика;
- `Infrastructure` - подключение к MySQL, инициализация базы и универсальный репозиторий;
- WPF UI - окна приложения и их обработчики.

Главная идея архитектуры: бизнес-логика и UI не пишут SQL и не знают, как именно данные сохраняются в MySQL. Все CRUD-операции выполняются через универсальный репозиторий `GenericRepository<T>`, который строит SQL автоматически по Reflection.

## 2. Слой Domain

Слой `Domain` содержит модели предметной области. Здесь нет SQL, MySQL-подключений, WPF-кода и бизнес-сервисов.

### `BaseEntity`

Базовый класс для всех сущностей:

```csharp
public abstract class BaseEntity
{
    public int Id { get; set; }
}
```

Все сущности наследуются от `BaseEntity`, поэтому универсальный репозиторий всегда знает, что у объекта есть первичный ключ `Id`.

### `TableAttribute`

Атрибут `TableAttribute` связывает C#-класс с таблицей базы данных:

```csharp
[Table("products")]
public class Product : BaseEntity
```

При добавлении новой сущности нужно только создать класс, унаследовать его от `BaseEntity` и указать `[Table("table_name")]`.

### `Product`

Модель товара:

- `Id` - идентификатор из `BaseEntity`;
- `Name` - название товара;
- `Quantity` - остаток на складе.

### `Arrival`

Модель прихода товара:

- `Id` - идентификатор;
- `DateTime` - дата прихода;
- `ProductId` - ссылка на товар;
- `Quantity` - количество товара в приходе.

### `Expense`

Модель расхода товара:

- `Id` - идентификатор;
- `DateTime` - дата расхода;
- `ProductId` - ссылка на товар;
- `Quantity` - количество товара в расходе.

### `IStorageDocument`

Интерфейс для документов склада. Его реализуют `Arrival` и `Expense`, потому что обе сущности имеют дату, товар и количество. Это позволяет сервису формировать итоги для приходов и расходов единым методом.

## 3. Слой Application

Слой `Application` содержит контракты и бизнес-логику. Он не зависит от MySQL и не содержит SQL-запросов.

### `IRepository<T>`

Универсальный интерфейс репозитория:

```csharp
public interface IRepository<T>
    where T : BaseEntity, new()
{
    List<T> GetAll();
    T GetById(int id);
    int Insert(T entity);
    bool Update(T entity);
    bool Delete(int id);
}
```

Интерфейс одинаков для любой сущности. Для новой сущности не нужно создавать отдельный репозиторий.

### `IStorageService`

Интерфейс сервисного слоя. Он описывает операции склада:

- получение товаров, приходов и расходов;
- добавление прихода;
- добавление расхода;
- обновление записей;
- удаление товаров и документов;
- формирование отчетов;
- подсчет связанных документов.

### `StorageService`

`StorageService` реализует бизнес-логику и работает только через `IRepository<T>`.

Сервис получает три репозитория:

```csharp
IRepository<Product>
IRepository<Arrival>
IRepository<Expense>
```

В сервисе нет SQL-запросов и классов MySQL. Например, при добавлении прихода сервис:

1. Проверяет название товара и количество.
2. Ищет товар через `products.GetAll()`.
3. Создает товар или увеличивает остаток.
4. Создает запись прихода через `arrivals.Insert(...)`.

При добавлении расхода сервис:

1. Проверяет ввод.
2. Ищет товар.
3. Проверяет, хватает ли остатка.
4. Уменьшает количество товара.
5. Создает запись расхода.

Каскадное удаление продукта также находится в сервисе. Сервис получает все приходы и расходы, связанные с товаром, удаляет их через репозитории, а затем удаляет сам товар. SQL-триггеры для этого не используются.

### `OperationResult`

Класс результата операции:

- `Success` - успешна ли операция;
- `Message` - сообщение для пользователя.

### `ReportSummary`

Класс итогов отчета:

- `TotalQuantity` - суммарное количество;
- `RecordCount` - количество записей.

## 4. Слой Infrastructure

Слой `Infrastructure` содержит реализацию работы с MySQL. Только здесь находятся MySQL-классы и автоматически сгенерированные SQL-запросы.

### `DbConnectionFactory`

Фабрика подключений к MySQL. Она читает строку подключения `StorageDb` из `App.config` и создает:

- подключение к конкретной базе данных;
- серверное подключение без выбранной базы для создания БД.

### `DatabaseInitializer`

Инициализатор базы данных. При запуске приложения он:

1. Проверяет наличие базы данных.
2. Создает базу, если ее нет.
3. Находит все классы-наследники `BaseEntity` с атрибутом `Table`.
4. Автоматически создает таблицы по свойствам сущностей.

Таблицы строятся универсально: имя таблицы берется из `[Table]`, а колонки - из публичных свойств класса.

### `GenericRepository<T>`

Универсальный репозиторий, похожий на упрощенный ORM.

Он использует Reflection для того, чтобы:

- определить имя таблицы;
- получить список свойств сущности;
- построить `SELECT`;
- построить `INSERT`;
- построить `UPDATE`;
- построить `DELETE`;
- преобразовать строку из `MySqlDataReader` обратно в объект.

Пример принципа работы:

- для `Product` репозиторий сам видит свойства `Id`, `Name`, `Quantity`;
- для `Arrival` сам видит `Id`, `DateTime`, `ProductId`, `Quantity`;
- для новой сущности он будет работать так же, без отдельного репозитория.

В проекте больше нет отдельных SQL-методов под каждую сущность вроде `GetAllProducts`, `AddArrivals`, `UpdateExpense` в репозитории. Это заменено универсальными CRUD-методами.

### `EntityMetadata`

Вспомогательный класс инфраструктуры. Он получает метаданные сущности:

- имя таблицы;
- список свойств;
- список свойств без `Id`;
- безопасное имя SQL-идентификатора.

## 5. WPF UI

WPF-окна работают только с `IStorageService`. Они не создают `MySqlConnection`, не используют `GenericRepository<T>` напрямую и не содержат SQL.

### `App.xaml.cs`

Класс `App` является composition root приложения. При запуске он:

1. Создает `DbConnectionFactory`.
2. Запускает `DatabaseInitializer`.
3. Создает три универсальных репозитория:
   - `GenericRepository<Product>`;
   - `GenericRepository<Arrival>`;
   - `GenericRepository<Expense>`.
4. Передает их в `StorageService`.
5. Открывает главное окно.

Окна получают сервис через `App.CurrentStorageService`.

### Главное окно

`MainWindow.xaml.cs` отвечает за:

- просмотр товаров;
- просмотр приходов;
- просмотр расходов;
- открытие окон добавления;
- открытие окон редактирования;
- удаление записей;
- открытие отчетов.

Главное окно не знает, как устроено хранение данных.

### Окна добавления

`AddArrivalWindow.xaml.cs` и `AddExpensesWindow.xaml.cs` проверяют пользовательский ввод и вызывают методы сервиса:

- `AddArrival`;
- `AddExpense`.

### Окна редактирования

`EditProductWindow.xaml.cs`, `EditArrivalWindow.xaml.cs` и `EditExpensesWindow.xaml.cs` загружают выбранный объект, дают пользователю изменить поля и передают объект в сервис.

### Окна отчетов

`IncomeReportWindow.xaml.cs` и `ExpensesReportWindiw.xaml.cs` получают период, вызывают методы сервиса и показывают результат в таблице. Итоги строятся через `ReportSummary`.

## 6. Добавление новой сущности

Чтобы добавить новую сущность, разработчику нужно:

1. Создать класс в `Domain`.
2. Унаследовать его от `BaseEntity`.
3. Указать атрибут `[Table("table_name")]`.
4. Добавить публичные свойства нужных типов.

После этого `DatabaseInitializer` сможет создать таблицу, а `GenericRepository<T>` сможет выполнять CRUD-операции для этой сущности без ручного SQL и без отдельного репозитория.

Пример:

```csharp
[Table("suppliers")]
public class Supplier : BaseEntity
{
    public string Name { get; set; }
    public string Phone { get; set; }
}
```

Для такой сущности можно создать `GenericRepository<Supplier>`, и стандартные методы `GetAll`, `GetById`, `Insert`, `Update`, `Delete` будут работать автоматически.

## 7. Итог

Проект переведен на расширяемую архитектуру с разделением слоев `Domain`, `Application` и `Infrastructure`.

Бизнес-логика изолирована от базы данных. UI изолирован от репозиториев и MySQL. Работа с данными выполняется через универсальный Reflection-based репозиторий, поэтому добавление новой сущности требует минимального кода и не требует ручного написания SQL под каждую таблицу.
